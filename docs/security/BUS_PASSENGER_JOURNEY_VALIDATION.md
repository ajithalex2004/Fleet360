# Item 3 — live passenger journey evidence

Passenger home and the mobile rider app fetch current manifest state without a session-long client cache. Each manifest row polls an employee-owned journey projection. It targets the recorded boarding stop before boarding and the recorded alighting stop afterward. The server resolves the authoritative staff relationship, checks tenant membership, locks the trip, filters current-vehicle GPS by departure/recovery time, and derives capacity/attendance aggregates within the tenant transaction. It returns no roster or other riders' identities.

The UI distinguishes live GPS (latest valid ping within two minutes), missing/stale GPS, planned timetable, disrupted service, a visited stop, and terminal travel. It never presents an old ETA as a live approach. The client also stops showing a previously fetched ETA after a failed poll or when the response/GPS becomes old. A recovered trip only accepts GPS following substitute assignment. A rider poll can claim the same atomic arrival/delay marker and outbox event used by the existing ETA route, preserving deduplication and opt-in notification rules.

Validation includes the unit cases for pickup/drop-off targeting, stale/future/recovery GPS, disruption, stop ambiguity and aggregate occupancy; the route tests check denial, tenant predicates, locking, failure behavior and notification intent. Chrome browser tests render the actual rider pages and styles with synthetic API responses at desktop/mobile widths and light/dark themes. PostgreSQL integration and signed-in staging with actual vehicle telemetry, attendance writes, tenant roles and notification workers remain release acceptance gates. No production messages or migrations were run by this item.
